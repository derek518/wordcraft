## 2. P0 缺陷

### D1 · 复习调度彻底失效（核心归零）

```rust
// db.rs:281 — days 参数被丢弃，"7天后"和"1天后"返回同一日期
fn add_days(date_str: &str, _days: i64) -> String {
    let parts: Vec<&str> = date_str.split_whitespace().collect();
    parts[0].to_string()
}
// db.rs:110 — 只捞 new 状态，复习过的词永不再现
if state.is_none() || state.unwrap().state == "new" { result.push(...) }
```

后果：**答过一次的词永远不会重来**，52 词答完 App 就空了。spec F2 验收「答错后 24h 内至少重现 2 次」= 0 次。

### D2 · 手写日期函数 85% 的日子算错

```rust
let secs_per_day = 86464u64;        // 应为 86400，每天多 64 秒
let year = 1970 + days / 365;       // 忽略闰年
let month = (day_of_year / 30) + 1; // 30天/月 → 可算出 13 月
```

未来 400 天实算：**340 天算错（85%），5 天算出不存在的「13 月」**。审计当日 2026-08-05 恰好落在正确的 15% 里——这正是它未被发现的原因。`review_logs` 时间戳全部污染，spec §6「算法可回溯调参」前提被破坏。

| 真实 | 算出 |
|---|---|
| 2026-08-05 | 2026-08-05 ✅ |
| 2026-08-31 | 2026-09-01 ❌ |
| 2026-11-29 | 2026-12-01 ❌ |
| 2027-03-29 | 2027-03-26 ❌ |

### D3 · `fix_db.py` — 把代码改坏的脚本

`src-tauri/fix_db.py` 删掉 `db.rs` 263–283 行的 chrono 日期函数，替换成上述错误实现。典型的「为绕过编译错误而破坏正确性」，正确做法是 `cargo add chrono`。**审计中最值得警惕的信号**：说明开发过程中存在「让它编过去就行」的取舍。

#### 补充证据（T02 执行时发现）

`src-tauri/target/debug/.fingerprint/` 中的旧构建指纹显示，项目**曾经依赖**：

```
chrono, tauri_plugin_sql, windows, reqwest, rand
```

正是 spec 要求的完整技术路线——真日期库、SQLite、全屏检测（`SHQueryUserNotificationState`）、Edge-TTS 网络请求、随机数。

**结论修正**：当前代码不是「尚未实现」，而是**「实现后被拆除」**。这解释了为什么模块分层与 command 命名看起来经过认真设计，实现却全为空壳。`fix_db.py` 是拆除过程的产物——移除 chrono 后需给日期函数找替代品，于是手写了 `86464` 那段。

**最可能的触发点**：`windows` crate 在 macOS 上编译失败 → 为让编译通过，将依赖逐一删除，连带拆掉依赖它们的实现。

**对 T03 的指导**：需要加回的依赖正是当初被删的那些；且必须将 Windows-only 依赖正确置于 `[target.'cfg(windows)'.dependencies]`，否则会重蹈覆辙。

> 此证据仅存在于 `target/` 构建缓存中，不入版本控制，且会被 `cargo clean` 抹除——故在此存档。

### D4 · 存储选型偏离 spec

两版 spec 均强制 SQLite + `tauri-plugin-sql`，实际用**单 JSON 文件全量读写**。每答一题触发「读全库 → 改一条 → 写全库」。52 词无感，5100 词 + 累积 logs 后每次答题 I/O 数 MB，且无事务、断电即全损。

### D5 · 硬编码 demo 数据（违反 `strict-execution-rules` §5.1）

```tsx
// WordTrainer.tsx:86 — 50 个写死的中文释义充当干扰项
const allMeanings = ['能力，才能', '能够的', '关于', ...]
```
```rust
// fsrs_engine.rs:67
fn generate_options(_correct: &str) -> Vec<String> {
    vec!["选项A".into(), "选项B".into(), "选项C".into(), "选项D".into()]
}
// scheduler.rs:31 — 永远返回 09:00 / 60 分钟后
```

spec F3 要求干扰项由编辑距离 + 同词性生成。且这 50 个释义恰好是当前 52 词的释义，**词库一扩就全线崩溃**。

### D6 · 前端 fallback 掩盖后端故障

```tsx

  console.error('Load words error:', e)
  const { newbieZoneWords } = await import('../data/words')  // 静默切假数据
```

### D7 · 词库 52 词且 100% 以 `a` 开头

「新手村 50 词」被实现成**字典序前 52 个**（ability/able/about/above/accept...），而非 spec §7.1 的按词频分层。`frequency_band` 手填无依据。
